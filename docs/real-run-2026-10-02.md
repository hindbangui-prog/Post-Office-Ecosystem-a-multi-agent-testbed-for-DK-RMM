# Real local run, 2026-10-02

This document records the first run of `tools/run_normal.py --ticks 300 --seed 1` against a
real Ollama server with a real `qwen3:8b`. The run was executed by the project owner on their
own Windows machine; every figure below is read from the six evidence files that run wrote to
`results\normal\s1\` (`verify.json`, `summary.json`, `consultations.json`, `llm_calls.json`,
`dkrmm.json`, `events.jsonl`) and from the console report. Nothing here was produced in the
development environment, which has no Ollama. The rules-only figures used for comparison come
from `tools/run_normal.py --rules --ticks 300 --seed 1`, which asks no model and is
deterministic for a seed, so it gives the same result on any machine.

the server behind that address is the one the owner runs.

## Decisions

300 ticks, 28 agents (the Planner and the six operational experts, all seven on the model;
15 sub-agents; 5 robots; the supervisor), 686 decisions in all.

| `deterministic` | 557 (81.2%) | 606 (100%) |
| `llm/conflict` | 49 | |
| `llm/failed` | 41 | |
| `llm/contention` | 26 | |
| `llm/ambiguity` | 1 | |
| `fallback` | 12 | |

The deterministic share of 0.81 on the real model is the rules-first property the suite pins
at 0.8 or more (`tests/test_rules_first.py`); the fake-model measurement during
implementation was 0.82. The model was asked 129 times, by three experts:

| Owner | Decision kind | Condition | Peer offered | Model decisions | Exchanges |
|-------|---------------|-----------|--------------|-----------------|-----------|
| SCHEDULING | `choose_next_task` | `competing_tasks` | DISPATCH | 47 | 0 |
| SCHEDULING | `choose_robot` | `equally_placed` | ROUTING | 38 | 0 |
| ROUTING | `resolve_block` | `still_blocked` | SCHEDULING | 41 | 3 |
| ROUTING | `resolve_block` | `expensive_detour` | SCHEDULING | 2 | 0 |
| INTAKE | `accept_parcel` | `unreadable` | (none) | 1 | 0 |

All 129 consultations closed `decided`; there was no `no_valid_decision`, `model_failed`,
`timeout` or `peer_failed`, and every brain's `fallbacks`, `retries`, `parse_failures`,
`rejected_answers` and `timeouts` counters are 0. The 12 decisions on the `fallback` path are
not model failures: in each the model named a robot that was on the allowed list but busy
(`MOVING`, `DELIVERING`, `UNLOADING` or `BLOCKED`), the policy gate refused the choice, and
SCHEDULING's rule chose the best-charged idle robot instead. The decision events carry the
refusal and the replacement in their `reason` field, for example tick 148:
`R1 is MOVING now; best charged of 2 nearby at 88.4%, 5 cells away`. The consultation rows
record the model's own choice (`source: crewai:qwen3:8b`, `outcome: decided`); the decision
event records what the simulator executed.

## Consultations with an exchange

In 126 of the 129 model decisions the owner answered alone, in one model call, without using
its one tool. In 3 it asked its peer. All three were ROUTING asking SCHEDULING under
`still_blocked`, and in all three the owner's decision followed the peer's advice:

| Id | Tick | Request (owner to peer) | Response (peer) | Decision | Latency |
|----|------|-------------------------|-----------------|----------|---------|
| CSL-0064 | 157 | What is the recommended action for resolving the block between R4 and R1, considering the battery level, ticks blocked, and detour distance? | Routing, the recommended action is to yield for R4 as it has the lowest battery level and the detour distance is minimal, which will help prevent further delays and conserve energy. Waiting would only prolong the blockage, and pushing could risk additional complications. Rerouting R4 would be the most efficient solution given the current constraints. | `YIELD` | 4569.9 ms |
| CSL-0067 | 160 | What is the recommended action for robot R5 when blocked by R3, considering battery, ticks blocked, direct distance, and detour extra? | R5 should yield to R3. The battery is low, and waiting would only delay progress further. Rerouting would add unnecessary ticks and risk further blockage. | `YIELD` | 4008.1 ms |
| CSL-0115 | 262 | What is the recommended action for resolving the blockage of robot R2 by robot R5, considering the battery level, detour distance, and time blocked? | The recommended action is to reroute R2 through the detour, as it allows R2 to proceed without waiting, which would delay the overall progress. Rerouting adds 2 units to the distance, but with R2's battery level of 78.6, it should be sufficient to complete the detour. This action minimizes the time blocked and ensures that R2 can continue its task efficiently. | `REROUTE` | 5069.7 ms |

Each of these consultations consisted of exactly three model calls, as the protocol requires:
the owner's first call, which produced the tool call (about 2.5 to 2.7 s, 128 to 133
completion tokens); the peer's single call with no tools (1.1 to 2.0 s, 35 to 85 tokens);
and the owner's second call, which read the peer's text from its tool result and wrote the
DECISION line (0.30 to 0.34 s, 6 to 8 tokens). The event stream holds the matching
`consult_opened`, `consult_question`, `consult_response` and `consult_closed` rows and three
`llm_call` rows for each, under one `correlation_id`. No consultation was refused and no
delegation was used.

## Latency and real time

Per model call (135 calls): minimum 199 ms, median 307 ms, 90th percentile 397 ms, maximum
2771 ms (the first call of the run, tick 17, presumably while the server loaded the model).
Per consultation (129): median 331 ms, maximum 5070 ms (CSL-0115 above). The median prompt
was 780 tokens and the median reply 8 tokens: with thinking off, qwen3:8b usually answers the
owner's task with a bare DECISION line.

| Owner to peer | Consultations | Median | Maximum |
|---------------|---------------|--------|---------|
| SCHEDULING to DISPATCH | 47 | 366 ms | 3696 ms |
| SCHEDULING to ROUTING | 38 | 335 ms | 1787 ms |
| ROUTING to SCHEDULING | 43 | 293 ms | 5070 ms |

The run took 62.1 s of wall clock for 300 ticks (from the first to the last event's
`wall_clock`). A tick without a consultation took about 1 ms; the 77 ticks with at least one
consultation took a median 0.37 s and at most 5.3 s. This is "real time" in the sense of
[consultation.md](consultation.md): every consultation completed inside the decision that
needed it, before the simulator executed that decision, within the 300 s deadline; no decision
waited for a late answer and none was taken without one.

| messages, events | 2130, 5303 | 2087, 4816 |

The model run completed fewer tasks and dispatched fewer parcels in the same 300 ticks, and
rerouted more. One run at one seed does not say whether that is the model's judgement
(choosing robots the rule would not, rerouting where the rule yields) or chance; the question
is open for the experiments that follow. What this run establishes is narrower and is the
point of the build: the seven experts run on CrewAI over a real local `qwen3:8b`, the
consultation protocol executes synchronously with the peer map enforced, the policy gate and
the rules remain the authority over what the simulator executes, every call is audited to the
configured server and model, and DK-RMM observes it all.

## What this run does not show

It is one run, one seed, 300 ticks, on one machine, with thinking off. It shows no model
failure mode (the counters are all 0), so the fallback paths for a malformed tool call, a
late peer or an HTTP error were exercised only by the test suite's fake. The share of
exchanges (3 of 129) is a property of qwen3:8b's behaviour under the current task text; a
different model or wording would give another share.
